# 示例：把反馈笔记整理成项目简报

[中文](project-brief.md) | [English](project-brief.en.md)

版本：1.1.0

以下是虚构教学材料。完整复制下列输入，任务不需要联网或附件功能。

## 可直接复制的输入

```text
输出语言：[中文 / English / 中英双语]
请用 AI 实干工作流，把以下反馈做成给设计同伴看的项目简报。
不要只列计划。先交一版简报，再给证据检查；总长不超过 700 字。

项目：图书交换活动的报名表。
材料：
[A] 试填记录：参与者甲在手机上填到“交换偏好”时停下，询问是否必填。
[B] 试填记录：参与者乙顺利提交，但表示不知道之后何时收到确认。
[C] 负责人记录：所有字段目前都设为必填；还没有正式报名数据。
[D] 现有流程：提交后页面只显示“提交成功”；负责人计划每周手动回复。

限制：这是两次试填，不代表全部用户。没有耗时、转化率或真实报名数据。
不要声称已经找到流失原因，不要替负责人承诺自动通知。

成品应包含：主要问题、每项判断的材料编号、至少一个替代解释、
可执行的下一步和一项待验证假设。保留当前手动回复的现实条件。
```

## 预期输出结构

1. **项目简报**：用现有材料说明问题与适用范围。
2. **证据表**：判断、材料编号、可以支持到什么程度。
3. **下一步**：给出现有流程下能做的修改建议和具体文案。
4. **待验证项**：写明假设、后续观察和无法由两次试填推出的结论。

## 可接受的参考片段

> 两次试填分别暴露了必填说明和提交后预期不清的问题：[A][C] 支持检查“交换偏好”的说明；[B][D] 支持补充回复方式与时间。现有材料无法确认报名流失或估计发生频率。
>
> 可先讨论“交换偏好”是否确有必要必填，并在提交页写明：“已收到你的报名。负责人将每周手动整理并回复。”具体回复渠道仍需负责人确认，不应凭空补上。

## 验收时看什么

- 不把两次试填写成大规模调研，也不出现虚构的转化率。
- 不把“甲停下询问”写成“甲已放弃报名”。
- 提出替代解释，例如“甲可能不理解问题本身”，而不只有必填状态。
- 区分当前可改的文案与尚未运行的后续测试。

此处是人工编写的参考结构与片段，不是已运行模型的测试输出。
